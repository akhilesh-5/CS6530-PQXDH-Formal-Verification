1. Project Motivation 
Migrating secure-messaging protocols to post-quantum cryptography is not simply a matter of replacing a classical 
primitive with a post-quantum algorithm. Security depends on protocol composition, binding between keys and 
identities, compromise assumptions, migration compatibility, and the relationship between specification and 
implementation. 
This project studies the progression: 
Deployed classical messaging key agreement -> post-quantum migration -> formal verification of specification and 
assumptions -> stronger subversion threats -> practical PQ protocol engineering 
The central Applied Cryptography principle explored by this project is: 
Post-quantum migration must preserve protocol security properties, not merely introduce a quantum-resistant 
primitive. 
2. Primary Paper - Mandatory 
[R1] Formal Verification of the PQXDH Post-Quantum Key Agreement Protocol for End-to-End 
Secure Messaging 
Karthikeyan Bhargavan, Charlie Jacomme, Franziskus Kiefer, and Rolfe Schmidt 
33rd USENIX Security Symposium (USENIX Security '24), 2024, pp. 469-486. 
The primary paper must be studied by all team members. 
Students should understand: 
• 
the role of X3DH and the motivation for PQXDH; 
• 
the harvest-now-decrypt-later threat and post-quantum forward secrecy objective; 
• 
the main entities, keys/prekeys and protocol relationships needed to reason about PQXDH; 
• 
the security questions addressed by ProVerif and CryptoVerif; 
• 
selected flaws or ambiguities identified in the specification; 
• 
why some theoretical specification issues were not exploitable in Signal because of implementation choices; 
• 
the additional KEM binding requirement highlighted by the analysis; 
• 
and how formal verification influenced the updated specification. 
Detailed mastery of every proof and every model in the artefact is not required. 
3. Supporting Literature - Guided Study 
The supporting papers extend the security perspective developed from the primary paper. They are not additional 
full-paper reproduction exercises. 
3.1 [R2] Subversion-resilient Key-exchange in the Post-quantum World 
Focus on how the threat model changes when the implementation performing post-quantum key exchange may 
itself be subverted, and on the role of subversion-resilient constructions and formal analysis. 
Guiding question: 
What additional protection is required if the PQ key-exchange implementation itself cannot be fully trusted?

3.2 [R3] A Post-Quantum End-to-End Secure Protocol for Instant Messaging Applications 
Focus on the clean-slate design of a PQ E2E messaging handshake, use of an untrusted relay, bidirectional KEM 
contributions, authentication, transcript binding and key confirmation. 
Guiding question: 
How does designing a new PQ E2E protocol differ from migrating an already deployed protocol such as Signal 
PQXDH? 
3.3 [R4] Design and Implementation of an Authenticated Post-Quantum Session Protocol Using 
ML-KEM, ML-DSA, and AES-256-GCM 
Use this paper primarily for its implementation and performance perspective: composing standardized PQ 
primitives with a KDF and AEAD, measuring overhead, and considering deployment constraints. 
Guiding question: 
What implementation and performance issues arise when standardized PQ mechanisms are assembled into a 
working secure-session protocol?

6. Activity 2 - Security and Specification Analysis 
Study selected findings reported by the primary paper. For the selected issue(s), distinguish: 
1. What security property was intended? 
2. What specification assumption or ambiguity was involved? 
3. What did the formal model reveal? 
4. Was the issue exploitable in the deployed Signal application? Why or why not? 
5. What implementation behaviour provided additional protection, if any? 
6. How was the specification changed or clarified? 
7. What cryptographic assumption or binding property is required for the corrected security argument? 
Select one finding suitable for deeper reproduction using the official artefact. 
7. Activity 3 - Bounded Reproduction 
Using the authors' official PQXDH analysis artefact, reproduce one selected formal-analysis result from an earlier 
specification/model and the corresponding corrected result. 
The project does not require reproduction of every ProVerif/CryptoVerif model in the paper. 
The reproduction should demonstrate: 
Earlier model/specification -> selected property or attack result -> corrected model/specification -> changed 
verification result 
ProVerif is the preferred mandatory reproduction path unless the selected result specifically requires CryptoVerif. 
The team should retain commands, model/version information and concise verification output as evidence. 
8. Activity 4 - Small Engineering Exploration 
Starting from the reproduced model, make one controlled modification to a relevant binding, distinction or 
compromise assumption. Examples may include algorithm/key-type distinction, KEM public-key binding, 
context/domain binding, or a selected compromise condition. 
Before modifying the model, state a hypothesis: 
What verification result do you expect after the change, and why? 
Run the modified model, compare it with the baseline, and explain the security meaning of the result. The objective 
is a bounded exploration, not redesign of PQXDH.

10. Activity 6 - Engineering Synthesis 
Based on the primary paper, supporting literature, security/design analysis, bounded technical study and 
engineering exploration, answer: 
Why is post-quantum migration of a deployed secure-messaging protocol more than replacing a classical primitive 
with a KEM? 
Identify four to five concrete engineering lessons supported by evidence and analysis from the project. 
What is an Engineering Lesson? 
An Engineering Lesson is a broader, generalizable conclusion synthesized from the project as a whole. Unlike an 
Engineering Implication in Activity 5, which is tied to one security dimension, an Engineering Lesson may combine 
evidence from the primary paper, supporting literature, security analysis, reproduction/experimentation, 
engineering exploration and multiple Security Evolution Matrix dimensions. 
An engineering lesson should explain what an engineer should consider, why it matters, and what security or 
operational consequence or recommended practice follows. It should be supported by project evidence or 
reasoning rather than stated as generic security advice. 
A useful way to formulate an Engineering Lesson is: Observation / Finding -> Why it matters -> Engineering lesson / 
recommended practice 
Illustrative Engineering Lesson: Adding a post-quantum KEM to a deployed messaging protocol does not 
automatically preserve the original security guarantees. This matters because identity/key binding, specification 
details, coexistence and implementation behaviour can change the resulting security argument. Therefore, PQ 
migration should be verified at the protocol and system level, not treated as a primitive substitution.

14. Generative AI Usage 
Use of Generative AI is permitted and encouraged as a learning and productivity aid. 
Appropriate uses include: 
• 
understanding unfamiliar cryptographic, protocol, system or formal-analysis concepts; 
• 
explaining algorithms, protocol flows, threat assumptions and paper terminology; 
• 
understanding author-provided artefacts, code, scripts, models and configuration; 
• 
assisting with student-developed code/scripts/models and troubleshooting environments; 
• 
planning experiments and controlled explorations; 
• 
investigating unexpected results and comparing observations with the literature; 
• 
comparing papers and organizing technical arguments; 
• 
improving clarity of technical writing, diagrams and presentation material. 
AI-generated material must not substitute for student understanding. 
Students are responsible for verifying AI-generated information against the primary/supporting papers, official 
documentation, source code/models and experimental evidence. 
The project workload already assumes reasonable use of AI. AI should enable better understanding, verification, 
experimentation and analysis within the available time, rather than increasing the amount of work assigned. 
A brief Generative-AI usage declaration should be included in the Technical Report.

16. Expected Learning Outcome 
At completion, students should be able to explain, using evidence from published research and formal-analysis 
artefacts, how post-quantum migration changes protocol assumptions and why specification, implementation 
and cryptographic binding must be analyzed together.
