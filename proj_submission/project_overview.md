## 2. Core Problem: Why Does This Project Exist?

### 2.1 The Harvest-Now-Decrypt-Later (HNDL) Threat
* Billions of instant messages today are encrypted using classical public-key cryptography—specifically **Extended Triple Diffie–Hellman (X3DH)** over Curve25519.
* Modern classical supercomputers cannot solve the discrete logarithm problem. However, a future **Cryptographically Relevant Quantum Computer (CRQC)** running **Shor's algorithm** will compute discrete logarithms in polynomial time.
* **The HNDL Threat:** Adversaries and state actors intercept and archive encrypted ciphertext streams **today**. Once a quantum computer becomes operational, they can retroactively decrypt the entire communication history of targets.

### 2.2 The Signal PQXDH Solution
To defeat HNDL while preserving classical security guarantees, Signal introduced **PQXDH**, a hybrid protocol that computes:
$$\text{Shared Secret} = \text{KDF}(\text{KMAC256}(DH_1 \parallel DH_2 \parallel DH_3 \parallel DH_4 \parallel SS_{\text{PQ}}))$$
where:
* $DH_1 \dots DH_4$ are classical Curve25519 Diffie–Hellman shared secrets;
* $SS_{\text{PQ}}$ is the shared secret generated by an IND-CCA2-secure lattice KEM: **ML-KEM-1024 (Kyber-1024)**.

### 2.3 The Core Vulnerabilities Analyzed
1. **The Gap in Generic IND-CCA2 Security (KEM Re-encapsulation):**
   * IND-CCA2 security guarantees ciphertext indistinguishability under a *single, fixed* public key.
   * IND-CCA2 does **not** guarantee public-key binding. An attacker knowing private key $SK_2$ for prekey $PQPK_2$ can take a ciphertext meant for $PQPK_2$ and re-encapsulate the exact same shared secret $SS$ into a ciphertext valid under Bob's honest prekey $PQPK_1$.
   * In Signal Revision 1, because Associated Data was only $\text{AD} = IK_A \parallel IK_B$, Bob accepted the session under $PQPK_1$, believing he had established an uncompromised session, whereas the attacker knew the session key.
2. **Key-Type Confusion:**
   * If public keys are represented as untyped byte strings (`encodeEC = encodeKEM`), an attacker can substitute Bob's classical Signed Prekey for a KEM prekey, forcing encapsulation against an elliptic curve point, producing a predictable secret (`weakECasKEM`) and stripping post-quantum protection.

## 5. High-Yield Viva Defense Preparation (5 Questions per Student)

The course evaluation includes an individual written viva on **Friday, 6 November 2026**. Below is an exhaustive study guide tailored specifically for each team member's domain, followed by cross-cutting questions.

### 5.1 Track 1: Akhilesh K.R (CS26E001) — Activities 1 & 2 Focus

#### Q1: What is the exact difference between classical X3DH and post-quantum PQXDH?
* **Answer:** Classical X3DH computes 3 or 4 Diffie-Hellman operations ($DH_1$ using identity keys and signed prekeys, $DH_2$ using ephemeral and identity keys, $DH_3$ using ephemeral and signed prekeys, and $DH_4$ using ephemeral and one-time prekeys) over Curve25519. In PQXDH, the initiator additionally generates an ephemeral encapsulation under Bob's Kyber-1024 public key ($PQPK_B$), yielding ciphertext $CT_{PQ}$ and shared secret $SS_{PQ}$. The root key derivation absorbs both:
  $$SK = \text{KDF}(\text{KMAC256}(DH_1 \parallel DH_2 \parallel DH_3 \parallel DH_4 \parallel SS_{PQ}))$$
  This ensures that even if a quantum computer breaks Curve25519, the session remains secure as long as Kyber is intact, and vice versa.

#### Q2: What is the "Primitive Substitution Fallacy" in post-quantum protocol engineering?
* **Answer:** It is the mistaken belief that migrating to post-quantum cryptography is a simple drop-in modular replacement of classical Diffie–Hellman with a post-quantum KEM. Diffie–Hellman is commutative and symmetric ($g^{ab} = g^{ba}$), providing implicit mutual authentication without signatures when identity keys are used. A KEM is strictly asymmetric (one party encapsulates, the other decapsulates). Inserting a KEM without re-architecting the protocol to bind public keys, ciphertexts, and transcripts to peer identities leaves the protocol open to active Man-in-the-Middle and key-splicing attacks.

#### Q3: Why does standard IND-CCA2 security fail to prevent KEM Re-encapsulation?
* **Answer:** IND-CCA2 (Indistinguishability under Adaptive Chosen-Ciphertext Attack) guarantees that an adversary given a fixed public key $pk^*$ cannot distinguish the decapsulation of a challenge ciphertext from a random secret, even with access to a decapsulation oracle. However, IND-CCA2 makes **no guarantees across different public keys**. It does not prevent an adversary possessing private key $sk_2$ from taking ciphertext $c_2$ and finding another ciphertext $c_1$ such that $\text{Decaps}(sk_1, c_1) = \text{Decaps}(sk_2, c_2)$. Public-key binding is an orthogonal property that must be enforced by the protocol.

#### Q4: If Signal Revision 1 was vulnerable to re-encapsulation in theory, why was the production Signal app safe?
* **Answer:** Because of an accidental implementation quirk in Kyber. Kyber uses the Fujisaki–Okamoto (FO) transform to achieve IND-CCA2 security from a passively secure PKE. Kyber's specific FO transform hashes the public key into the shared secret:
  $$SS = \text{KDF}(m \parallel H(pk))$$
  Because $H(pk_1) \ne H(pk_2)$, the resulting shared secrets were mathematically distinct, neutralizing the attack in software. However, this was an implementation accident. Had Signal substituted Kyber for FrodoKEM or Classic McEliece lacking this hash, the protocol would have been immediately broken. Hence, Bhargavan et al. required Signal to issue Revision 2 to codify this binding explicitly in the specification.

#### Q5: What is Key-Type Confusion, and how does Signal prevent it?
* **Answer:** Key-type confusion occurs when different cryptographic primitives use ambiguous, untyped bitstring encodings. If a Curve25519 public key and a Kyber-1024 public key are both formatted as raw byte arrays, a malicious server or attacker can substitute an EC Signed Prekey ($SPK$) into the slot expected for a KEM prekey ($PQPK$). Signal prevents this by prepending rigid single-byte domain separators: a `0x05` prefix byte for Curve25519 public keys and a dedicated prefix byte for Kyber public keys, preventing algebraic coercion.

### 5.2 Track 2: Mysha Ali (CS26E008) — Activity 3 Focus

#### Q1: What is ProVerif, and what attacker model does it assume?
* **Answer:** ProVerif is an automated formal verification tool for cryptographic protocols based on the applied pi-calculus. It models cryptography symbolically (the Dolev-Yao model), treating cryptographic primitives as black-box algebraic constructors and destructors with rewrite equations. The adversary has total control of the public network: they can eavesdrop, intercept, forge, reorder, splice, and inject messages, but cannot break cryptographic primitives unless they possess the corresponding keys or exploit specified algebraic properties.

#### Q2: How did you model the KEM Re-encapsulation attack in ProVerif for Revision 1?
* **Answer:** Since ProVerif assumes perfect cryptography by default, a standard KEM model would enforce that ciphertexts under different public keys always yield independent secrets. To model generic IND-CCA2 KEMs without public-key binding, we added an explicit rewrite rule:
  ```proverif
  fun reencaps(bitstring, kem_sk, kem_pk): bitstring.
  equation forall m: bitstring, r: bitstring, sk1: kem_sk, pk2: kem_pk;
    decaps(reencaps(internal_enc(kem_pk_from_sk(sk1), m, r), sk1, pk2), sk_from_pk(pk2)) =
    decaps(internal_enc(kem_pk_from_sk(sk1), m, r), sk1).
  ```
  This allowed the symbolic attacker, given knowledge of $sk_1$, to transform a ciphertext under $pk_1$ into a ciphertext valid under $pk_2$ producing the identical shared secret.

#### Q3: What is "Injective Agreement", and what does it mean when ProVerif says `RESULT inj-event(...) ==> inj-event(...) is false`?
* **Answer:** Agreement guarantees that if Bob finishes a protocol session believing he communicated with Alice on a set of parameters, Alice did indeed execute the protocol with Bob on those exact parameters. **Injective** agreement adds a one-to-one relationship, ensuring that for every session Bob completes, there is a unique corresponding session initiated by Alice (preventing replay attacks). When ProVerif outputs `is false`, it means the solver found a counterexample trace where Bob completes a session under parameters ($PQPK_1$) that Alice never agreed to (she used $PQPK_2$), or where multiple responder sessions map to a single initiator session.

#### Q4: Exactly how does Signal Revision 2 fix the re-encapsulation vulnerability?
* **Answer:** In Revision 1, the Associated Data (AD) for the symmetric AEAD initial message was $\text{AD} = IK_A \parallel IK_B$. In Revision 2, Signal modified the Associated Data to explicitly include Bob's KEM public key:
  $$\text{AD} = IK_A \parallel IK_B \parallel PQPK_B$$
  When the attacker intercepts Alice's message (encrypted with $\text{AD} = IK_A \parallel IK_B \parallel PQPK_2$) and delivers the re-encapsulated ciphertext to Bob under $PQPK_1$, Bob attempts to decrypt the AEAD payload using $\text{AD}' = IK_A \parallel IK_B \parallel PQPK_1$. Because the AEAD tag covers the Associated Data, the tag verification fails, and Bob immediately aborts the handshake.

#### Q5: What are the execution metrics and outputs of your Activity 3 models?
* **Answer:** In our automated test suite (`run_all.ps1`):
  * Model 01 (`01_pqxdh_rev1_reencaps_vulnerable.pv`) ran in **23.77 seconds**, successfully extracting the active re-encapsulation attack trace.
  * Model 02 (`02_pqxdh_rev2_hardened.pv`) ran in **20.73 seconds**, evaluating 6 internal verification stages and mathematically proving `RESULT inj-event(RespondDone(...)) ==> inj-event(InitDone(...)) is true`.

### 5.3 Track 3: D R Santhosh (CS26E004) & Akhilesh K.R (CS26E001) — Activity 4 Explorations Focus

#### Q1: What was the motivation behind Exploration 1 (Key-Type Confusion), and how did Santhosh model it?
* **Answer:** In cryptographic engineering, bugs often arise at format boundaries. We wanted to test what happens if an implementation fails to enforce distinct types between classical Curve25519 public keys and Kyber-1024 public keys. In `03_activity4_confuse_kem_ec.pv`, Santhosh created a rewrite rule allowing an EC public key to be converted into a KEM public key:
  ```proverif
  reduc forall x: G; asKEM(encodeEC(x)) = kem_pk_from_ec(x).
  equation forall x: G; encaps(kem_pk_from_ec(x)) = (encaps_weak(x), weakECasKEM).
  ```
  When the initiator encapsulates against this coerced key, it produces a predictable secret (`weakECasKEM`). ProVerif evaluated the query `event(InitDone) && attacker(weakECasKEM)` and proved that an attacker can force this downgrade in 15.90 seconds.

#### Q2: What is Proposal P2 (Direct KDF Transcript Binding), and how did Akhilesh formulate it?
* **Answer:** Signal Revision 2 solved the re-encapsulation problem by modifying the AEAD Associated Data. However, this conflates layer boundaries: it uses a symmetric payload encryption mechanism to patch an asymmetric key-agreement binding defect. In Proposal P2 (originally proposed during Revision 3 discussions), the Associated Data remains purely classical ($\text{AD} = IK_A \parallel IK_B$), but Bob's KEM public key ($PQPK_B$) is fed directly into the root HKDF extraction:
  $$SK = \text{HKDF}(\text{KMAC256}(DH_1 \parallel DH_2 \parallel DH_3 \parallel DH_4 \parallel SS \parallel PQPK_B))$$

#### Q3: Why is Proposal P2 mathematically superior to Revision 2's AEAD Associated Data fix?
* **Answer:** Proposal P2 achieves **cryptographic layer separation**. In Revision 2, if an application developer uses PQXDH to derive a session key but sends an unauthenticated plaintext payload, or uses an AEAD cipher that ignores Associated Data, the re-encapsulation attack resurfaces. Under Proposal P2, the session key $SK$ itself is cryptographically bound to $PQPK_B$. If an attacker attempts re-encapsulation under $PQPK_1$, Alice and Bob derive completely different session keys ($SK_2 \ne SK_1$). The protocol is protected at the root key derivation level, independent of the application layer.

#### Q4: How did ProVerif verify Proposal P2 in `04_activity4_pqxdh_kdf_bound.pv`?
* **Answer:** In `04_activity4_pqxdh_kdf_bound.pv`, we retained the vulnerable re-encapsulation equation for the KEM, but updated the KDF constructor to absorb `PQPKB_p` on the initiator side and `PQSPKB_p` on the responder side. When ProVerif ran the injective agreement query, it evaluated to:
  ```text
  RESULT event(RespondDone(b,a,useOPK_2,opk,spk,pqpk,ts))@i_1 ==> 
         (useOPK_2 = True && event(InitDone(a,b,True,opk,spk,pqpk,ts))@i) is true.
  ```
  The proof completed in **20.21 seconds**, verifying that binding $PQPK$ directly into HKDF completely stops re-encapsulation.

#### Q5: What are the trade-offs between Proposal P2 and Signal Revision 2 in practice?
* **Answer:** Signal chose Revision 2 (AD binding) because it preserved backward compatibility with their existing HKDF key derivation routines; modifying HKDF inputs would have altered the root key format across all client versions. Proposal P2 is cryptographically cleaner and more robust, but requires updating the root KDF specification. Our formal verification proves both are secure, but Proposal P2 provides better layer encapsulation.

### 5.4 Cross-Cutting Questions (All Team Members)

#### Q1: How does PQXDH compare to the protocols in Supporting Literature [R2], [R3], and [R4]?
* **Answer:**
  * **Signal PQXDH [R1]:** A hybrid retrofitting of an existing classical protocol (X3DH) using Curve25519 + ML-KEM-1024. Designed for asynchronous store-and-forward messaging.
  * **Duverger et al. CCS '25 [R2]:** Focuses on subversion resilience—analyzing what happens if the post-quantum RNG or primitive implementation itself is backdoored.
  * **Abiega-L’Eglisse et al. '26 [R3]:** A clean-slate post-quantum instant messaging protocol that discards classical Diffie–Hellman entirely, using pure post-quantum ratchets.
  * **Olushola & Meenakshi '26 [R4]:** A standalone synchronous session protocol combining ML-KEM-512, ML-DSA-44 (Dilithium-2), and AES-256-GCM.

#### Q2: What is the post-quantum bandwidth and MTU challenge?
* **Answer:** Classical Curve25519 public keys are 32 bytes and signatures are 64 bytes. In contrast, ML-KEM-1024 public keys are 1,568 bytes, and ML-DSA-44 signatures are 2,420 bytes. While acceptable in asynchronous messaging (adding ~1.5 KB per prekey bundle), in interactive UDP/datagram networks, an initial handshake combining KEM and signature exceeds the 1,500-byte Ethernet MTU (~4.5 KB total), forcing 4-way IP fragmentation and causing severe packet loss on cellular links.
